2. What Sprint 3 is, and how we did it

The brief calls Sprint 3 Representation & Clustering: "section statements into leaf topics". Its tasks: choose a representation and store it in the shared database, fit and compare at least two clustering methods, run a parameter sweep with a stability report, and decide whether a statement may belong to more than one topic. Deliverable: topic and topic-membership tables plus the stability report with chosen parameters.

Step 2 in detail: cleaning the skill names

Each name becomes its own point in the embedding space, so "excel" and "microsoft excel" would split counts and blur topics. Four rules merge names: R1 hyphens and punctuation (problem-solving = problem solving), R2 "ms" → "microsoft", R3 drop a trailing "skills", R4 a human-verified alias list.

The R4 list came from a cross-check with independent signals: spelling rules (plurals, spaces, "(ap)"), a level or vendor word ("adobe photoshop" = "photoshop"), near-identical embeddings, and the same ESCO / O*NET entry. All 289 high and medium candidates were checked against the posting text: 269 merged, 16 kept apart. Kept apart, for example: canvas (Canvas LMS) ≠ canva, "SAPs" (lab analysis plans) ≠ SAP, routings (manufacturing) ≠ routing (networks), CMM (measuring machine) ≠ CMMS. Pairs found only by meaning were usually broad vs narrow ("trend analysis" vs "market trend analysis") and were not merged.

Weakness found: the embedding sees only the name. numpy lands next to "basic math", tensorflow next to airflow ("-flow"), and "microsoft excel" falls between the Microsoft products topic and the spreadsheet topic. Planned fix in Sprint 4: embed the name plus a short description.

MethodHow it groups skillsBest settingTopicsCoverageAMIVerdict

Agglomerative (cosine)merges the closest pairs step by step, cut at a distancecut 0.4357100%0.61hierarchy only

  • HDBSCAN gives the steadiest topics on the skills it clusters, and honestly marks 22% as "does not fit". We keep those skills as weak members, so none is lost.
  • Leiden RB covers every skill and has the best per-topic overlap (Jaccard 0.60), but its labels move more between subsets (AMI 0.75). On the 78% that HDBSCAN clusters, the two agree (AMI 0.78, uncleaned run), so the choice is mainly about the hard 22%.
  • Leiden CPM was suggested by a GPT review as "steadier as data grows". Our test said no: best per-topic Jaccard 0.53 vs 0.59 for RB.
  • Agglomerative is the least stable on raw skills and jumps from thousands of tiny clusters to one giant cluster within a small change of the cut. We keep it only for the Sprint 4 hierarchy over topic centres.
  • k-means needs the number of topics in advance and cannot leave a skill out, which does not fit skill data (topics range from 10 to 90+ skills).

4. Our skill library work

Why we built a skill library

Clustering groups skills by what they mean, using only the skill name. It never looks at which jobs use a skill. That leaves a gap for the generic skills that every sector asks for. We built the library for four reasons:

ReasonWhat happens without itWhat the library adds
1. Generic skills get strandedHDBSCAN puts many of them in noise (attention to detail has no topic at all) or in separate soft-skill topics (39 topics), cut off from the domains that use themEach generic skill is linked to the domain topics it really appears with
2. Our end goal needs themFor an initiative like "build a finance team" we could return accounting topics, but not that the same postings also ask for excel and attention to detailLinks found in real postings: microsoft excel → payment reconciliation (lift 3.2)
3. The brief asks for it"Decide whether a statement may belong to more than one topic" would be answered with one topic per skill only A library skill belongs to its own topic and links to several domain topics: our multi-topic answer
4. It prepares Sprint 5Task ↔ skill mapping would start from zeroThe same co-occurrence maths (lift, p, q per template) will link Section A's tasks to our skills

Example: communication appears in 603 postings across all 8 sectors. Its meaning puts it in a soft-skill topic, which tells us nothing about where it matters most.

The idea. Keep two things apart: topics (meaning, from embeddings) and a library of cross-sector skills linked to the domain topics they really go with (from counting postings). The library is a label on a skill, so nothing is duplicated.

Who is in the library

  • A skill seen in ≥ 5 postings, in ≥ 4 of 8 sectors, with no sector holding more than 50% of its postings. Confirmed = ≥ 10 postings. The rule was fixed before looking at the results.
  • 196 library skills (146 confirmed). Only 43 of them are HDBSCAN noise; the rest also have a normal topic.
  • Each has a type from its ESCO / O*NET link: 80 skill · 55 knowledge · 27 tool (excel, word) · 6 trait (attention to detail, leadership) · 28 unknown.
  • 39 soft-skill topics (more than half their mentions are library skills) are flagged transversal.

How a library skill links to a topic

  1. Count job templates (company + job title) that mention the skill, the topic, and both.
  2. Lift = observed ÷ expected by chance. Example: excel 191 postings, the accounts-payable topic 41, of 1,931 → chance ≈ 4 shared, seen 18, lift ≈ 4.4.
  3. p = hypergeometric test (could the overlap be luck?); q = Benjamini–Hochberg correction over all 65,584 pairs tested.
  4. Strong when ≥ 5 templates, lift ≥ 1.5 and q < 0.05; otherwise weak. Result: 980 links, 249 strong (e.g. microsoft excel → payment reconciliation, lift 3.2).

Limits to say out loud

  • About half the topics are fragile under resampling, for every method.
  • The embedding uses the name only; topic labels are still the centroid skill (the coding topic shows "scala").
  • Small sample (1,931 postings); the Qwen batch is slowed by the free tier, so the snapshot mixes Qwen and the Haiku research run.
  • Library thresholds were set by us and are not yet tested for sensitivity; sectors come from noisy LinkedIn tags.
